OpenScience can run analysis on your machine or use resources you connect. Model access and compute are separate: an Ace Wallet does not include unlimited experiments on external machines.

## Local analysis

Open **Customize → Compute** and check the Python and R starter setup. If either needs setup or repair, use the offered action and wait for it to finish.

The Python starter includes common analysis libraries such as NumPy, pandas, SciPy, and Matplotlib. The R starter includes tidyverse, ggplot2, and jsonlite. Additional tools may need a separate installation or account.

Shell and local compute receipts identify the selected default Python separately
from any measured version. A command can explicitly choose another interpreter,
so this default is not proof of which Python an arbitrary shell command used.
On Windows, `python` selects this default; an independently installed `python3`
or an absolute executable path can select another interpreter.
Local compute using the default Python measures that binary in the admitted execution environment.
Remote submissions label local source metadata as belonging to the submitter;
an unmeasured remote interpreter is left unknown.

Local compute on Windows requires Git Bash. If discovery fails, install Git for
Windows or set `OPENSCIENCE_GIT_BASH_PATH` to its installed `bash.exe`. OpenScience
reports a missing or incompatible shell before dispatching a POSIX job script.

Try a small task first:

```text
Check that Python can read data/samples.csv and save a histogram to
results/sample-counts.png. Explain any missing dependency before changing
the environment.
```

## Scientific tools

Open **Customize → Tools** to see which scientific tools are available on the device or through a connected account. Follow a tool's setup action when offered.

A skill can describe how to use a package without that package being installed. See [Scientific tools](/openscience/scientific-tools) for availability and limitations.

## Connect your own remote resources

The Compute panel supports configured services and SSH hosts. Use your own account or machine credentials, then test the connection.

For an SSH host, supply the host details or import an existing SSH configuration, verify the connection, and record any scheduler or working-directory requirements. Supported scheduler choices are shown in the panel.

For a connected compute service, review its resource defaults and timeout before asking for a job. Saving a credential alone does not guarantee that every service feature is supported.

## Approve a concrete run

Before launching a paid or substantial experiment, ask OpenScience to state the inputs, resources, duration, output files, and estimated cost if available.

```text
Prepare a pilot using the configured remote host. Show the command,
resource request, input files, and expected output location. Ask before
launching, and stop after the pilot so we can review the result.
```

Use the external service's spending controls as well as a task budget. Its charges are governed by that service's terms.

## Follow progress and collect outputs

Use the project's **Compute** view to inspect jobs. Ask for current status, failures, and saved outputs when a task is long-running.

If a response is interrupted, check whether the job is still running before starting another. Stopping a chat response is not proof that every external job has stopped.

After completion, ask OpenScience to retrieve the output files, verify that they are readable, and report the exact project paths. A remote job marked complete is only useful if its results are available for review.

## Monitor node resources

Open the project's **Compute → Resource monitor** while an analysis is running.
Automatic selection follows a running or queued job in the current session,
then a running or queued allocation in the project, and otherwise the connected host. Select a target
explicitly to keep monitoring it. Multi-node allocations offer a node selector.
Manual target and node choices remain selected as live inventories refresh or
change order; choose **Automatic · active job** to resume following active jobs.
The connected host can be a login node; its resources are labelled separately
from an allocated compute node.

CPU and system memory charts appear alongside one chart per accelerator. Solid
lines show device compute utilization; dashed lines show memory utilization.
Use the 1, 5, or 15 minute history range, hover or focus a chart and use the arrow
keys to inspect samples, or pause and resume updates. CPU and system memory describe
the whole node, including other workloads. **Allocated accelerators** lists only
devices verified for the selected job on the selected node. Device metrics cover
those devices' total usage, including any sharing; they are not process-exclusive
measurements. A standalone host shows **Visible accelerators** instead.
TPU compute utilization is the runtime duty cycle reported
by `tpu-info`.

| Environment | Telemetry source |
| --- | --- |
| Local Windows, Linux, macOS; connected remote workspaces | OS CPU counters and memory |
| NVIDIA GPUs | `nvidia-smi` |
| Hygon DCUs | Verified Linux DRM/sysfs devices for Slurm allocations; `hy-smi` JSON or legacy tables on standalone hosts |
| AMD GPUs | Verified Linux DRM/sysfs devices for Slurm allocations; `rocm-smi` JSON on standalone hosts |
| Cloud TPUs | `tpu-info` runtime utilization and HBM table |
| Slurm allocation | Current user's queue, allocated node list, then SSH or an overlapping sampling step within that existing allocation |
| PBS allocation | JSON job status and `exec_host`, then SSH to an allocated node |

Monitoring uses administrator-owned clients from the backend's environment.
On Windows, NVIDIA sampling preserves the system installation directories needed
by NVML. Failed queries include the driver's diagnostic message when available.
Node sampling requires `/usr/bin/python3`; it uses only Python's standard library.
SSH host keys must already be trusted. Slurm's fallback requires support for
`srun --overlap` and permission to create a step in the existing job. Monitoring
does not submit new jobs. Standalone host CPU/memory sampling does not require
Python or a scheduler. A running supported TPU workload and an installed
`tpu-info` client are needed for TPU runtime metrics.

Jobs submitted through the compute broker retain their session association.
For Slurm/PBS jobs submitted directly from a shell, discovery matches the job's
working directory against the current project/session's connected directories.
Jobs in a shared project folder are labelled as project allocations rather than
assigned to an arbitrary session. Jobs submitted from unrelated directories must
use the compute broker to retain their association. Managed services that do not
expose node telemetry report it as unavailable.

Samples refresh approximately every five seconds while the **Compute tab remains
open**, including while viewing Files or other modules and while the inspector is
collapsed. Slow probes never overlap. Switching modules preserves up to 15 minutes
of in-memory history; switching conversations restores their separate target and
node histories. Pause suspends sampling; closing the Compute tab with its **×**
ends monitoring and releases its history. Browsers may suspend background pages
or sleeping computers; those interruptions are shown as gaps when sampling resumes.
A lost connection preserves the last values and
marks them stale. Queued, finished, unsupported, and permission-denied states are
shown explicitly. A dash means the metric is unknown, not zero utilization.

A resource read that stops responding is released after 30 seconds, including when the response body stalls. The monitor keeps the available history and retries automatically; a late response cannot replace a newer sample.

On supported Linux nodes, kernel device metrics identify cards by stable PCI
addresses, so a scheduler's logical device renumbering cannot merge histories
from different physical cards. For Slurm AMD/Hygon allocations, the monitor checks
the scheduler's per-node device count, the sampler's exact job cgroup, and access
to each physical render device. Unallocated devices are excluded. Missing or
inconsistent allocation evidence hides accelerator readings with an explanation;
CPU and system memory remain available when the node is reachable. CPU-only jobs
show that no accelerators were allocated. PBS and other accelerator configurations
without a verified device mapping also report the limitation rather than showing
the whole node's cards as job resources. Standalone NVIDIA, AMD, Hygon and TPU
monitoring remains available. The monitor also supports
Hygon's standard `/opt/hyhal` installation and clients reporting `HCU` utilization
or VRAM in MiB. Node collectors work with older Python runtimes in the C locale.

Both the local backend and the backend on a connected remote workspace must be
updated to expose the monitoring endpoint.

## When setup fails

Check the error shown by Compute, available disk space, network access, credentials, and the requested resource type. Keep the failed job identifier when asking for help.

For a tool marked unavailable, choose a supported alternative or resolve the stated prerequisite. Do not assume that a different model can remove a missing dependency or account requirement.
