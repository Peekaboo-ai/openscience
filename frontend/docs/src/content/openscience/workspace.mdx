The desktop app and browser workspace give you the same research workflow: open a project, choose a model, and work through a question in a conversation.

On Windows, the customized **OpenScience Workspaces** EXE installer provides a desktop and Start menu shortcut. Double-click the shortcut to enter the local workspace and start its backend; no separate server command, Synthetic Sciences account, or sign-in key is needed. Official account sign-in remains optional in Settings. Its settings and research data live in `%LOCALAPPDATA%\OpenScience Workspaces` and remain after upgrading or uninstalling. The installer does not include another user's model keys, SSH settings or conversations. Configure model access and remote hosts on first use.

Desktop SSH connections support data paths containing spaces and Chinese characters. Imported hosts still require a successful connection test to pin their public host keys; remote projects continue to use strict host-key verification.

```bash
openscience
openscience ~/research/my-project
```

The first command opens the current folder; the second opens the folder you specify.

## Projects and conversations

A project groups related work and files. A conversation, also called a session, holds the requests and results for one task. Start a new conversation for a separate question, or reopen an existing one to continue its work.

Give files descriptive names and tell OpenScience where to save outputs. A new conversation does not automatically know every detail of another conversation; refer to the relevant saved report or handoff when continuing across sessions.

## Action Timeline

Open **Action Timeline** in the workspace sidebar or compact workspace menu. An **action** is an observable step taken to carry out a research request: a model response, tool call, analysis, delegation, retry, context compaction, or recorded file snapshot. A request is the starting point that groups these steps; its redacted text summary names the group. A step's completion does not certify the scientific validity of its result. Model-response intervals can include tool execution, so their durations can overlap.

The list shows descriptive action names, human-readable outcomes, and the active project's model/provider names. **Needs review** isolates failed, interrupted and partially completed steps while retaining their request context. Step numbers describe order within the loaded request history; filtering preserves them, and loading earlier steps can extend that numbering. A request whose starting message is outside the loaded history is labelled accordingly.

Select an action to inspect its outcome, token breakdown and recorded cost. **Recorded timestamps (UTC)** and **Technical identifiers** reveal exact timing and runtime IDs when needed for diagnosis. Narrow panels keep duration in the list; token details remain available in the inspector. Raw tool arguments, outputs, provider protocol state, synthetic system prompts, and reasoning text are excluded. Use the original conversation to review a tool's full inputs, outputs, or a provider error. A recorded zero cost can mean missing price metadata, not a free request.

The first page contains the latest 50 messages. **Load earlier** adds older history; search only covers records already loaded. Search temporarily expands matching turns, preserving their previous folded state when cleared. **Follow latest** returns to current work. The timeline refreshes from persisted state after streaming events and reconnects; a failed request retains the last successful snapshot and shows an error.

Expand **Timing overview & time filter** to use its buttons or mouse wheel to zoom, Shift/right-drag to pan, and drag to filter by time. The exact-time controls provide a keyboard alternative. The action list supports arrow keys, Page Up/Down, Home, and End. Missing timing phases and unknown measurements display as unavailable rather than estimated zeroes. **Session controls & recovery** contains the following existing workbench operations.

**Save checkpoint** creates a research handoff document under `.openscience/checkpoints` and freezes a recovery recipe from the durable execution history. **Recovery plan** shows each step, source generation, code digest and whether it can be replayed safely. **Recover to new branch** copies the checkpoint conversation and replays verified literal state in separate Python/R kernels; the original session and kernels are preserved. This is conservative replay, not an arbitrary memory image: imports, unknown dependencies, file/network effects and nonliteral state require manual review. Such recipes are marked **partial**, never complete. Recovery logs survive reloads, show progress/failures, and allow review and retry in another fresh branch. Current permissions and interpreter availability still apply.

**Fork session** copies the conversation; action details can fork before a selected message and checkpoints can fork at their saved boundary. **Branch lineage** links related sessions. **Undo from this message** first previews affected messages/actions and tracked files, then uses native conversation/file undo. **Restore undone conversation** is available before a subsequent prompt. Conversation undo does not rewind kernel variables, and recovery replay does not roll back files. **Fresh restart** clears a kernel's variables after confirmation.

The workbench also supports cancellation of a specific active runtime run or compute job, and **Guide / Stop** controls for an owned running child agent. Guidance joins the child's current execution loop. Kernel history reports the latest 200 executions, including independent REPL cells, exact queue timestamps and generations. Context composition is the last recorded request estimate, separately labelled from provider-reported usage; it is absent when no request telemetry is available.

The workbench also shows child agents, compute jobs, the latest provider-reported context usage, and actual kernel sandbox/permission state. Reasoning tokens are already included in output tokens. The view distinguishes an empty session from unavailable or stale data.

## Add context

Mention the input files and the outcome in your request. The file picker and attachments let you provide material directly. You can also use `@file` references where the composer offers them.

```text
Use data/samples.csv and methods/protocol.md. Check whether the sample
labels match the protocol, and save discrepancies in results/labels.md.
```

Only refer to material you have permission to use. For large files, first ask for the schema or a bounded sample.

## Follow progress and steer the task

The conversation shows the agent's prose in bright text and everything it did to get there in grey beneath one header per turn: thoughts (with their text when the provider shares it), files read, searches, commands, edits, delegations and questions, in order. While the turn runs the header names the call in flight ("Reading study.json") and the list is open; when it finishes the header reads "Worked for 46m 29s" and folds the list, leaving the answer, any failed call and any question that still needs you. Open an individual row when you need a tool's inputs or output.

You can send follow-up prompts while a response is running: they join the current turn and the agent answers them in order. Use the **Stop** button or Escape when you need to change direction immediately. Inspect any files already written before asking it to retry or redo the work.

Use [Research controls](/openscience/agents) to choose planning, research effort, delegation, and when the agent asks for your input.

## Review files and scientific results

Open an output link in the conversation or choose **Files**. Supported scientific formats can display as plots, molecules, structures, or genomic views.

**Project files** and **Session scratch** are different locations. They can contain files with the same name. Check the preview's location, especially when opening an older conversation, and save final deliverables to the project.

Ask for a text explanation alongside a visual result: what was measured, what the axes or colors mean, and where the source data came from. See [Files and storage](/openscience/files).

## Undo and restore

After a response finishes, use **Undo from here** to return to an earlier point. Review the confirmation, which identifies affected work and file changes. A restore action is available for reverted work.

Undo is useful for trying a different analysis path. It does not reverse external payments, messages, or changes in a connected service. Use version control or backups for files you need to retain independently of conversation history.

## Browser and terminal sessions

Adding or updating model connections keeps existing terminal tabs and their shell state. Rotating or removing a key still interrupts requests and processes that used the previous credentials. Project access revocation and stopping the backend can still close terminals.

Project conversation lists appear immediately when reopened after their first load, then refresh in the background. Local and remote projects keep separate caches. A failed refresh preserves the last loaded list and shows a retry action.

The CLI prints a local workspace URL. If you close the browser tab while the command is still running, reopen that URL. Stopping the CLI stops that running workspace; saved conversations remain available next time.

To choose a port:

```bash
openscience web --port 4096
```

For a browser-free server and a request from another terminal:

```bash
openscience serve --port 4096
openscience run --attach http://localhost:4096 "Summarize the current project"
```

Use the actual URL printed at startup. The workspace is for local access; it does not provide public remote hosting.

See [Sessions](/openscience/sessions) for continuing, exporting, and importing conversations.

## Messages while a task is running

With a draft in the composer, **Guide now** sends a follow-up for the agent to read at its next step. It does not interrupt a running command. The separate Stop control (or Escape) cancels the current run.

While a task runs, **Enter** sends guidance to its next step. Open the arrow beside Send and choose **Add to queue**, or press **Ctrl+Enter** (⌘+Enter on macOS), to save a separate task for execution after the current run. Selecting either menu action sends the current draft immediately. Queued messages retain their attachments, selected model and reasoning settings on the connected backend, including remote projects. You can edit their text, reorder or remove them, and pause or resume the queue. Stopping a run, a failed run, or a backend restart pauses pending work; review it before resuming. A stopped backend does not silently replay work whose effects may already have occurred.

Permission buttons show a pending state immediately and prevent duplicate decisions. Connection failures keep the request available for retry. Waiting for approval is labelled separately from command execution. Shell timeouts show their configured limit instead of hiding the reason in diagnostic metadata. Action Timeline keeps its loaded history when you switch modules; workbench summaries update separately.

Shell activity cards distinguish environment preparation, process startup, command execution, and result collection. Ordinary commands use the host shell environment without installing a Python runtime. Conda/venv activation applies to commands in the same Shell call; it does not change other calls or an already-open interactive terminal. The optional `environment: "python"` setting selects an existing OpenScience Python runtime and its project packages explicitly.
